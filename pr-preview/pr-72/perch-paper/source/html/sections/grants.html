A grant is a set of rules; each names one contract, the functions it may call, conditions on the arguments, who must sign, when it ends and how much it may spend in a sliding window.

Perch has two kinds of JSON document. An account document sets the owner's own policy: administrative rules, signers and recovery configuration. A grant document describes a bounded set of rules for an app. Installing a grant document creates or replaces an installed grant: rules and metadata stored under a grant ID and stamped with the current grant generation, a counter that only a completed recovery advances. The document is an input and a hash commitment; the installed grant is the permission the account consults.

A grant document

{
  "version": 1,
  "network": "{{fact:standalone-passphrase}}",
  "signers": [
    { "id": "app", "verifier": "C…(Ed25519 verifier)", "key": "…Ed25519 public key, hex…" }
  ],
  "rules": [{
    "name": "spend",
    "scope": { "type": "contract", "address": "C…(native XLM contract)" },
    "principals": { "type": "all", "signers": ["app"] },
    "functions": ["transfer"],
    "cap": { "limit": "{{fact:grant1-cap-stroops}}", "period-ledgers": {{fact:grant1-period-ledgers}} }
  }]
}

This is grant 1 as the experiment installs it, with addresses and the key abbreviated; network is the passphrase of a local standalone network. scope is the rule target, here the native XLM contract. principals is the signer condition, here the one signer app. functions restricts calls to transfer. cap.limit is {{fact:grant1-cap-xlm}} XLM in stroops ({{fact:stroops-per-xlm}} to the XLM) as a decimal string; the cap charges the amount argument of transfer(from, to, amount), and a rule may carry a cap only if its functions are exactly ["transfer"]. The signer names its verifier by address alone, which Perch treats as unverified: allowed in grants, but each such verifier may supply at most one signer per rule ({{ref:sec:authorization}}).

The game grant that Nido's testnet preview installed adds what this one lacks: an address-eq condition on argument 1 that pins the recipient to the game, a not-after-ledger expiry on both rules, a cap of {{fact:preview-game-cap-xlm}} XLM per {{fact:preview-game-period-ledgers}} ledgers ({{fact:preview-game-period-label}}), and a passkey signer. {{ref:sec:compare}} writes it out in full.

What a rule can check

A rule allows a call when four things hold: the called contract is the rule's target; the function is in the rule's list, or the rule lists none; every argument condition holds; and enough of the rule's signers have signed to meet its threshold. A document can write {{fact:doc-conditions-count}} argument conditions: {{fact:doc-conditions}}. They require, in turn, the account's own address, one given address, one of several strings, a string prefix, and one u32 value. Every condition in a rule must hold; a document has no or and no not. A rule may also end at a ledger ({{fact:perch-expiry-semantics}}) and carry a cap.

A document cannot bound a single call's amount. On a capped rule, lowering adds only a type guard that argument 2 is an i128; the cap bounds the total in a window, not each transfer.

Installing a grant

Installing takes two contracts: the stateless document compiler, which parses and checks the JSON, and the account, which lowers the result into rules and stores them. In order:

  1. The owner authorizes apply_grant (exported as apply_scope; {{ref:tab:tab-api}} maps every name). The account calls the compiler, which parses and validates the JSON, resolves verifier names through the perch/verifiers registry, and returns canonical bytes, their hash doc_hash, a model of the document, credential fingerprints and a normal-form flag.
  2. The account refuses with ScopeEscalation a grant that configures recovery, and reads its excluded set: its adopted recovery controller, and the zero-knowledge adapter and pool of its recovery configuration.
  3. It lowers the model with rule-core's lower_scoped under its own address, the excluded set and the current grant generation. The lowering and containment theorems cover this function (T8, T9, T12). A refusal surfaces as ScopeEscalation, or as UnguardedRule for a rule with no signer.
  4. It refuses with NotNormalForm a document that is not in normal form, which allows one spelling per meaning.
  5. It refuses with RevokedCredential or WipedCredential a credential that a recovery revoked or that a stale grant named.
  6. It reconciles rules by name and drops the spending records of removed or changed rules.
  7. It stores the grant record, rule tags and index entry. Spending records are separate entries that only authorization writes.

Grant lowering refuses a document that configures recovery, and any rule whose target is the account, its adopted recovery controller, or the zero-knowledge adapter and pool of its recovery configuration (lib.rs:1218-1240, 1328-1345).

The account stores no grant JSON. A grant's rules and the metadata to rebuild it (generation, document hash, signer IDs and verifier names) share one persistent record; an index enumerates grants, and rule tags connect a selected rule ID to its grant. Because the account accepts documents only in normal form, a client can rebuild the canonical JSON from chain state and check it against the stored doc_hash, the SHA-256 of the document's CANON v1 bytes.

Canonical bytes and doc_hash

CANON v1 is Perch's canonical JSON: RFC 8785 {{cite:rfc8785}} restricted to what Perch documents contain. A Lean package in Perch proves the encoding injective on the modeled document type (T13). The CANON version is not part of the hashed bytes, so a doc_hash is read under the identity the account reports (capabilities().doc_identity); configPreimage_ne_emitDoc, rulePreimage_ne_configPreimage and rulePreimage_ne_emitDoc prove that configuration, rule and document hash preimages never coincide. Account document bytes are kept on chain, because recovery derives its target document from them.

What a set of rules means

A rule set allows the union of what its rules allow: an action is permitted when some rule permits it. The account does not search for that rule. The authorization payload names one rule per context, and the named rule must itself allow the context, so naming the wrong rule refuses a context that another rule would allow. The named rule must also be unexpired and, if it carries a generation, current. A supplied signer that belongs to no chosen rule is refused, not ignored.

Attenuation derives a narrower rule set from an existing one, for example to hand part of an app's authority to a helper. rule-core defines exactly {{fact:attenuation-steps}} attenuation steps; each returns a rule set that allows nothing the original does not, and none changes a rule's target or generation. Two theorems state this ({{ref:sec:proofs}}): narrowing for single actions (T4), and trace inclusion (T5), which says that any sequence of authorizations the child accepts from empty spending records, the parent also accepts. These are results about rule-core's model and its translation: the account cannot install an attenuated grant at the pinned build ({{ref:sec:agents}}).

Sliding windows

A capped rule charges the i128 amount at argument 2. For a period of P ledgers, the window at ledger L holds the charges made after L − P and through L; a new charge is accepted when the window's total plus the charge stays at or below the limit. Contexts in one authorization that select the same rule each see the earlier charges in that batch, and a refusal leaves the spending record unchanged. From empty records, an accepted history keeps every window of a capped rule within its limit (T6). A negative or malformed amount, overflow, a ledger earlier than the newest charge and a full history fail closed.

On chain the history bound is the size of one ledger entry, not the evaluator's {{fact:evaluator-history-bound}} entries. A spending record takes {{fact:spend-record-base-bytes}} bytes plus {{fact:spend-record-per-spend-bytes}} per spend, so the network's {{fact:ledger-entry-limit-bytes}}-byte entry limit holds {{fact:spends-per-window}} spends per window. Further capped transfers through that rule fail until older spends leave the window, so a grantee can exhaust its own rule's window with small transfers.
