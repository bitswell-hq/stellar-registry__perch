The account checks the grant before it checks any signature, and writes spending records only when every check passes.

The evaluator's interface

Two functions have similar names. Soroban calls the account's __check_auth, which calls the account-shell function perch_smart_account::check_auth; that function runs the guards below and then the evaluator, rule_eval::authorize in rule-core {{fact:rule-core-pin-short}}. The evaluator takes the selected rules, their spending records, the converted contexts, one local rule index per context, the claimed signer identities, the ledger and the grant generation. It returns the next spending records, aligned with the input rules, or a Refusal. It neither searches for rules nor verifies signatures; the account shell, the contract code around it, does both.

// Pinned build: perch-smart-account/src/gate.rs, calling rule-core {{fact:rule-core-pin-short}}
let after = rule_eval::authorize(
    &rules,                 // the selected rules, each once
    &records,               // their spending records
    &contexts,              // host contexts, converted
    &choices,               // one local rule index per context
    &signers,               // claimed signer identities
    e.ledger().sequence(),
    scope_generation(e),    // the grant generation
)
.map_err(|r| match r {
    rule_eval::Refusal::StaleGeneration => PerchAuthError::StaleScope.into(),
    _ => refused(),         // RuleEvalRefused
})?;

The evaluator refuses misaligned inputs, an expired, stale or non-matching rule, an unused signer, or a failed charge, each as a distinct Refusal. The account keeps one distinction: a stale grant becomes StaleScope (auth error {{fact:auth-error-stale-scope}}) and every other refusal RuleEvalRefused (auth error {{fact:auth-error-rule-eval-refused}}). These are __check_auth's own codes, which the host reports inside {{fact:host-auth-error}} and logs in its diagnostic events; a wallet that needs the reason re-runs the evaluator off chain. The evaluator accepts an empty batch vacuously, but the host never passes zero contexts (T11).

One authorization, step by step

{{ref:fig:fig-check-auth}} traces one authorization. Four guards run before any rule is read: reserved hook names are refused on any contract (step 1); a recovery completion is recognized (step 2); while a recovery under the Protected profile, which assumes the owner's key may be stolen, holds the account, everything but its completion is refused (step 3); and each selected grant rule is checked against the account's current excluded set (step 4). A completion leaves at step 4 and is decided by the recovery controller, so a recovery completion never depends on the evaluator.

Step 4 is the runtime half of containment. The account may adopt a recovery controller after a grant is installed, so __check_auth compares each selected grant rule's call with the excluded set as it is now and refuses with ScopeEscalation (auth error {{fact:auth-error-scope-escalation}}). The install-time property has theorems; this recheck is tested shell code.

What a signature binds

For the original address credential, the host's signature payload ({{ref:sec:background}}) does not name the account; CAP-0071's address-bound credentials add it. Perch binds the account either way. The account hashes that payload with its own {{fact:contract-id-bytes}}-byte contract ID under the domain tag {{fact:auth-domain-tag}}, so two accounts that share a key and rule IDs cannot reuse each other's signatures; it then appends the selected rule IDs and hashes again. An external signer signs that digest, so a relayer cannot move the signature to another rule the signer belongs to, such as an uncapped one.

A delegated signer never sees that digest. It approves the host's address-bound payload, which names the account but not the rule IDs, so whoever submits the transaction may select any rule that lists the delegate. OpenZeppelin {{fact:oz-v080-tag}} binds the rule IDs for delegated signers too, so on that path it binds more than Perch. A document should not place one delegate in rules of different strength and expect the weaker rule to bind it. {{ref:tab:tab-binding}} sets the two designs side by side.

{{table:tab-binding}}

A credential's authority is the union of every live rule that names it. Binding the rule IDs stops a relayer, not the signer, from choosing among those rules.

The digest names rule IDs, not rule contents or the account's revision. A rule the owner edits in place between signing and inclusion decides under its new contents, so wallets keep signature expirations short; a removed or replaced rule fails closed, because rule IDs are never reused. apply_grant takes no expected version, so two pre-signed installs for one grant ID can land in either order before they expire.

Verifiers

An external signer pairs key material with a verifier, a contract implementing verify(digest, key, signature) -> bool. Ed25519 {{cite:rfc8032}} and WebAuthn {{cite:webauthn2}} (passkey) verifiers are deployed; a verifier for {{fact:mldsa-verifier}} {{cite:fips204}}, a post-quantum signature scheme, is built and tested but in neither manifest. The shell authenticates every claimed signer, which is the evaluator's assumption. Both deployed verifiers trap on a bad signature rather than return false, so a failed signature fails in the host's signature check ({{fact:verifier-trap-error}} for Ed25519); ExternalVerificationFailed ({{fact:oz-error-external-verification-failed}}) is raised only for a verifier that returns false; the built {{fact:mldsa-verifier}} verifier is one. One {{fact:mldsa-verifier}} signer does not make an account post-quantum: the owner's passkey, Ed25519 guardians and the zero-knowledge factor are not. The compiler refuses any key not already in its verifier's canonical form, so one key has one spelling, and a threshold, which counts distinct identities byte for byte, cannot count it twice. The WebAuthn verifier checks the assertion type, the challenge, the user-presence, user-verification and backup flags and the P-256 signature, but not the relying-party ID or origin, the fields that tie a passkey to a website; binding a passkey to a site is the wallet's and authenticator's job.

The account derives each infrastructure address, the document compiler's among them, under the current network ID from a Wasm hash and registry path fixed at build time; the derivation calls nothing. Once the pinned code is deployed on a network, no registry action changes it, and an account reaches a new compiler only through its own delayed upgrade. An account document must name each verifier through the perch/verifiers registry, for example {{fact:verifier-name-webauthn}}. A verified name means the registry deployed that code at its own hash; its manager decides which hashes it deploys, and its admin can replace the registry's code. One key holds both roles on testnet and mainnet. A grant document may name a verifier by address alone; each such unverified verifier may supply at most one signer per rule, so it cannot cast several threshold votes in one rule, though it can cast its one vote at will.

{{fact:reserved-hook-count}} reserved hook names ({{fact:reserved-hook-names}}) are refused on every contract before any rule is read, so the recovery controller's hooks are reachable from the account's own code and from nowhere else. install, uninstall and enforce are OpenZeppelin's policy hook names. A recovery completion carries no signatures, so anyone may submit and pay for it; selecting the recovery rule in any other shape is refused.

For wallet and dApp developers

  • Simulate twice. Recording simulation does not call __check_auth, so it cannot predict a Perch refusal or the reads __check_auth makes. Sign the entry with the selected rule IDs, then simulate again with enforcing authorization to learn the verdict and the final footprint. This paper's driver does the same.
  • Choose the rules. The authorization payload names one installed rule per context in context_rule_ids, in context order. A refusal reports auth error {{fact:auth-error-stale-scope}} or {{fact:auth-error-rule-eval-refused}} and nothing more, so re-run the evaluator off chain to learn which context failed.
  • Build documents. The TypeScript package in packages/perch-js has a builder that produces validated documents, canonical JSON and doc_hash, and helpers for account reads, rule selection and authorization construction. Its requestToPolicyDoc turns an ERC-7715-shaped permission request into a grant document. A generated JSON Schema for documents is described in docs/schema.md.
  • Try it. The Nido preview creates accounts on the testnet deployment ({{ref:sec:status}}); this page runs the same contract source offline in the live experiment.
