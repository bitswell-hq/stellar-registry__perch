The proofs cover the rule check, not the compiled contract, the host, or what happens outside an authorization.

The limitations are grouped by the proofs, the shell, and the adversaries of {{ref:tab:tab-adversaries}}.

The proofs and the binary

The theorems are about the translation of the MIR that rustc {{fact:rustc-mir-nightly}} produces. rule-core's CI also builds the evaluator with rustc {{fact:rustc-rule-core-stable}}, Perch builds its contracts with rustc {{fact:rustc-perch}}, and nothing checks the Wasm against the translation ({{ref:fig:fig-proof-paths}}). Release builds keep overflow checks and abort on panic, and allocation failure and stack exhaustion, which the functional model omits, also trap, so each fails the transaction. The specification is itself trusted: the denotation functions; the document meaning Doc.allows, written from Perch's earlier account ({{fact:doc-allows-source}}, on OpenZeppelin's library at {{fact:oz-fork-pin}}) and not re-derived from the pinned gate; and the Soroban host models.

The shell and the host

Tested, not proved: the JSON parser and compiler, stored-value decoding, rule-ID resolution, context conversion, assembly of the excluded set, spending-record persistence, the credential index, the generation update, the composition of evaluation with authentication, and the recovery controller's state machine. The integration tests run the account's real __check_auth under enforcing authorization, but as natively registered contracts; the Wasm with passkeys and real proofs runs in Perch's release_stack.rs flows and on testnet. The host models are tested against selected traces, not proved equivalent to soroban-env-host, and leave out TTL, archival, fees, footprints and validation before the host runs; this paper's simulator is another tested host integration. No single theorem covers the whole pinned gate, including mixed administrative and grant batches; the argument in {{ref:sec:proofs}} rests on tested obligations.

Against a grantee (A1)

A key named by several live rules holds the union of their authority, and caps are per rule, not per grant. Each context is checked alone, so a rule meant for a call the game makes also allows that call made directly ({{ref:fig:fig-contexts}}, case c). A capped rule's window holds at most {{fact:spends-per-window}} spends. Replacing a capped rule, or changing its cap in either direction, starts an empty window, so lowering a cap right after a grantee spent up to it allows the new limit again within the same window. A standing token allowance used by transfer_from, or funds held by another contract such as the game's payout, can move value without a fresh authorization, and recovery, grant removal and the Protected freeze leave such allowances usable. A grant rule on a token contract that does not restrict its functions also allows approve. An owner-authorized execute(target, function, args) runs as the account, so the callee's require_auth passes by invoker authority and no rule or cap sees it; grants cannot reach execute, but an administrative rule that allows it has unlimited authority over the targets it permits. Policy evaluation provides no confidentiality or information-flow control.

Against a submitter (A2)

Delegated signers do not bind rule IDs ({{ref:tab:tab-binding}}). A rule edited in place between signing and inclusion decides under its new contents. A refused entry can be resubmitted until its expiration ledger. Grant installs take no expected version, so two pre-signed installs for one grant ID can land in either order.

Owner-key theft and recovery (A3, A4)

Losing every factor the recovery condition needs remains loss, and Protected without an enrolled baseline protects against a stolen owner key no better than Loss, under which a thief can cancel any recovery. A full guardian quorum is trusted. Outside an authorized recovery attempt, the owner may schedule a code upgrade and execute it after {{fact:upgrade-delay-ledgers}} ledgers ({{fact:upgrade-delay-days}}); any change of the recovery generation makes the request stale, and under Protected the recovery condition must approve the exact Wasm hash. New code inherits the account's storage, including the revoked set and the generation, and nothing in the old code can make it honour them; the proofs cover the examined code, not replacement code.

One documented deferral bears on recovery: the account consumes a completion marker by the target's canonical identity, not its exact bytes. If a completion authorization whose apply_doc never ran left a marker, an owner-authorized write of a differently spelled version of the same target in the same ledger is classified as the completion and runs its revocation, nullifier and generation effects (issue {{fact:completion-marker-issue}}). It cannot install a different policy.

Components the account trusts (A5)

The account trusts its verifiers to check evidence, and the recovery controller its account document names to decide completions. Unlike verifiers, the controller gets no registry provenance check, so wallets should pin the published controller's content address. The perch/verifiers registry's manager admits verifier names and its admin can upgrade the registry; one key holds both roles on testnet and mainnet, and names resolved by later installs follow the manager. The WebAuthn verifier does not bind an origin, and a wallet must show what the signed payload commits to.

Resources and review

Bounded records and arithmetic can refuse a logically permitted action. Documents are capped at {{fact:doc-max-signers}} signers, {{fact:doc-max-rules}} rules, {{fact:doc-max-canonical-bytes}} canonical bytes and {{fact:doc-max-rule-name-bytes}}-byte rule names; the caps are meant to keep a thief holding the owner key from making recovery too expensive to complete. A lost-key completion at those caps (combined, ZK rotation, in process) uses {{fact:worst-case-completion-share}} of the {{fact:tx-instruction-limit}} instruction limit, and disk-read bytes are not yet measured. The account's renew does not extend installed-grant records, so an idle account may need a restore before its next transaction ({{ref:tab:tab-ending}}). No external audit has been completed ({{ref:sec:status}}).
