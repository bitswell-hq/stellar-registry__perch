What a signature commits to

For an ordinary address credential, the host's signature payload (§01) does not name the account. The account hashes that payload with its own 32-byte contract ID under the domain perch/account/auth-addr-v1, so accounts sharing a key and rule IDs cannot reuse each other's signatures, then appends the selected rule IDs and hashes again (Figure 7). An external signer signs that digest, so a relayer cannot move the signature to another rule the signer belongs to, such as an uncapped one. The digest names rule IDs, not rule contents or the account's revision: a rule the owner edits in place between signing and inclusion decides under its new contents, so wallets keep signature expirations short, while a removed or replaced rule fails closed because rule IDs are never reused.

{{fig:fig-7}}

A delegated signer (CAP-0071) never sees that digest. For an entry that carries delegates, the host hashes an address-bound preimage that names the account but not the rule IDs, so whoever submits the transaction may select any rule that lists the delegate. A document should not place one delegate in rules of different strength and expect the weaker rule to bind it. The evaluator checks the selected rule's generation before the host asks the delegate, so a stale grant is refused first.

Ordinary RPC simulation records authorization without calling __check_auth, so it cannot predict a Perch refusal or the reads __check_auth makes. A wallet, like this paper's driver, signs the selected rule IDs and simulates again with enforcing authorization to learn the verdict and the final footprint.

A verifier identifies how evidence is checked

An external signer pairs key material with a verifier contract implementing verify(digest, key, signature) -> bool. Ed25519 and WebAuthn verifiers are deployed; an ML-DSA-65 verifier is built and tested but in neither manifest. The shell authenticates every claimed signer, which is the evaluator's assumption. The compiler refuses any key not already in its verifier's canonical form, so one key has one spelling and a threshold, which counts distinct identities byte for byte, cannot count it twice; the constructor also refuses two administrative signers that are one key. The WebAuthn verifier checks the assertion type, the challenge, the user-presence, user-verification and backup flags and the P-256 signature, but not the relying-party ID or origin; binding a passkey to a site is the wallet's and authenticator's job.

In the pinned build, the constructor accepts an external administrative signer only if its verifier sits at the content address its Wasm hash derives in the perch/verifiers registry, a derivation that calls nothing. An account document must name each verifier through that registry (for example perch-webauthn-verifier@0.1.2), and the compiler resolves the name by calling it. A verified name denotes provenance admitted by the registry's manager, not a proof or an audit. A grant document may name a verifier by address alone; each such unverified verifier may supply at most one signer per rule, so it cannot cast several threshold votes in one rule, though it can cast its one vote at will.

Ten reserved hook names (install, uninstall, enforce and seven rcv_* names) are refused on every contract before any rule is read, so the recovery controller's hooks are reachable only from the account's own code. A recovery completion carries no signatures, so anyone may submit and pay for it; selecting the recovery rule in any other shape is refused.
