A grant is a set of rules, each naming one contract, the functions and arguments it allows, who signs, when it ends and how much it may spend in a sliding window.

A grant document and an installed grant

A grant document is the JSON the owner submits; {{ref:fig:fig-shop-grant}} shows one. The owner installs it by calling the account's apply_scope (the code calls a grant a scope). The account passes the JSON to the document compiler, a stateless contract that parses and validates it. The account then lowers the result into stored rules with lower_scoped from rule-core, the library that holds Perch's decision function {{cite:rule-core}}. It lowers under its own address; its grant generation, a counter that only a completed recovery advances; and its excluded set, the contracts its recovery uses. Lowering refuses any rule whose target is the account itself, its adopted recovery controller, or the zero-knowledge adapter and pool of its recovery configuration ({{ref:stmt:grant-target-containment}}; lib.rs:1218-1240, 1328-1345). What it stores is an installed grant: the rules the account consults on every call. The full install path, with its seven steps, canonical bytes and document hash, is in the vision paper.

What a rule checks

A rule allows a call when four conditions hold: the called contract is the rule's rule target; the function is in the rule's list, or the rule lists none; every argument condition holds; and enough of the rule's signers signed to meet its threshold, counted over distinct signers. A document can write {{fact:doc-conditions-count}} argument conditions, {{fact:doc-conditions}} (doc.rs:281-304), and all of a rule's conditions must hold. A rule may end at an expiry: {{fact:perch-expiry-semantics}}. It may carry a cap only when its functions are exactly ["transfer"], and the cap charges the transfer's amount.

Selection is explicit. The authorization payload names one rule for each context, and that rule must itself allow the context; the account does not search for another. A signer that belongs to no chosen rule is refused, not ignored.

The spending window

A cap is a limit \(\lambda\) and a period \(P\) in ledgers. The window at ledger \(L\) holds the charges made at ledgers \(t\) with \(L - P < t \le L\). A new charge is accepted when the window's total plus the charge stays at or below \(\lambda\), and the account keeps these charges in a spending record in its own storage. The check is part of the decision that checks the call, so there is no separate step to skip. Contexts in one authorization that select the same rule each see the earlier charges in that batch, and a refusal changes nothing.

{{ref:fig:fig-cap-window}} plays the shop grant against this definition. With JavaScript it is an explorable: set \(\lambda\) and \(P\), send amounts, advance the ledger, and compare with checking each call alone. Its "Replace the rule" toggle shows what happens when the owner replaces a capped rule: the new rule starts with an empty window. {{ref:stmt:cap-window-safety}} states the bound: from empty records, no window holds more than \(\lambda\). On chain a spending record lives in one ledger entry, which holds at most {{fact:spends-per-window}} spends, so further transfers through that rule fail until older ones leave the window.

Handing part of a grant to a helper (modelled; not installable at this build)

An app may want to pass part of its grant to a helper, such as a sub-agent. Attenuation derives a narrower grant from an existing one. rule-core defines {{fact:attenuation-steps}} attenuation steps, among them dropping a rule, removing functions, adding an argument condition, raising a threshold, lowering a cap's limit, lengthening its period and moving the expiry earlier; none changes a rule's target. {{ref:stmt:attenuation-narrows-authority}} proves that a derived grant allows nothing its parent does not. That is a result about the model and its translation: the account has no entry point that installs an attenuated grant at the pinned build. An account entry point for attenuated grants is proposed (the vision paper).

Ending a grant

{{ref:tab:tab-revoke}} lists the three ways a grant stops: its expiry, one owner call to remove_scope, or a completed recovery. A stopped grant's storage stays until someone collects it, and gc_scope lets anyone do so.
