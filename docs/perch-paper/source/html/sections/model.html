An account document describes the owner's account policy, including administrative rules and recovery configuration. A grant document describes a bounded set of rules for an application. Applying a grant document creates or replaces an installed grant: rules and metadata stored under a grant ID, stamped with the current grant generation. A document is an input and hash commitment; an installed grant is the persistent permission the account consults.

    { "id": "app", "verifier": "C…(Ed25519 verifier)", "key": "…32-byte public key, hex…" }
  ],
  "rules": [{
    "name": "spend",
    "scope": { "type": "contract", "address": "C…(native XLM contract)" },
    "principals": { "type": "all", "signers": ["app"] },
    "functions": ["transfer"],
    "cap": { "limit": "100000000", "period-ledgers": 100 }
  }]
}

This is grant 1 as §10 installs it, with addresses and key abbreviated. scope is the rule target (the native XLM contract), principals the signer condition (the one signer app), and functions restricts calls to transfer. cap.limit is 10 XLM in stroops as a decimal string; the cap charges the amount argument of transfer(from, to, amount), and a grant may cap only a rule whose functions are exactly ["transfer"]. The signer names its verifier by address alone, which Perch treats as unverified: allowed in grants, but each such verifier may supply at most one signer per rule (§06).

The game grant that Nido's testnet preview installed adds what this one lacks: an address-eq condition on argument 1 that makes the game the only recipient, a not-after-ledger expiry on both rules, a cap of 2 XLM per 17,280 ledgers (one nominal day), and a passkey signer named perch-webauthn-verifier@0.1.2.

Compilation, installation and reconstruction

Installing a document takes two contracts (Figure 4). The stateless document compiler parses and validates the JSON, resolves named verifiers by calling the verifier registry, and returns canonical bytes, their hash doc_hash and a model. The account lowers the model itself, with rule-core's lower (account documents) or lower_scoped (grants), under its own address, its current excluded set and the current grant generation; these are the functions the lowering and containment theorems cover. Grant lowering refuses rules that target the account or its recovery infrastructure, so a grant cannot install recovery configuration or give an app administrative authority.

A grant's rules and reconstruction metadata (generation, document hash, signer IDs and verifier names) share one persistent record; an index enumerates grants, and rule tags connect selected rule IDs to their grant. The account stores no grant JSON. It accepts only grant documents in normal form, one spelling per meaning, so a client can rebuild the canonical JSON from chain state and check it against the stored doc_hash. Account document bytes are kept for recovery derivation. doc_hash is the SHA-256 of the document's CANON v1 bytes, Perch's canonical JSON (RFC 8785 restricted to what Perch documents contain); §09 states what is proven about it.
