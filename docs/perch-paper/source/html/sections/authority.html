A rule allows a call when its target, function policy, argument conditions and signer threshold hold. A rule set denotes the union of its rules' permissions, but the account does not search it: the rule named for a context must itself allow that context, so naming the wrong rule refuses a context the union allows. The selected rule must also be unexpired (its last valid ledger is inclusive) and, if it carries a generation, current. A supplied signer that belongs to no chosen rule is refused, not ignored.

Attenuation narrows authority. Rule-core defines exactly ten attenuation steps (Table 2); each returns a rule set that allows nothing the original does not, and none changes a rule's target contract or generation. Two theorems state this (§09): narrowing for single actions, and trace inclusion for whole histories from empty records. Neither bounds the combined spending of a grant and the grants derived from it, or of siblings; that needs the delegation-tree budget model below or shared records. Attenuated grants are modeled and proven in rule-core; the account cannot install them at the pinned build.

Sliding windows and shared budgets

A capped rule charges the I128 amount at argument 2, the amount of transfer(from, to, amount). The engine filters the rule's history to the current window, checks the new total and returns a new record; contexts that select the same rule each see the batch's earlier charges, and a refusal yields no partial next state.

For a period of P ledgers, the window at ledger L holds the charges made after L − P and through L. From empty records, an accepted history keeps every such window of a capped rule within its limit (§09 states the exact theorems). Malformed amounts, overflow, a ledger earlier than the newest charge and a full history fail closed. On chain the history bound is the ledger-entry size, not the evaluator's 1,000 entries: a spending record is one entry of 172 bytes plus 72 per spend, so the network's 65,536-byte limit holds 907 spends per window, and further capped transfers through that rule fail until older spends leave it. A grantee can therefore exhaust its own rule's window with small transfers.

A separate delegation-tree budget model charges spending to ancestors: child allowances may oversubscribe a parent, yet spending beneath each node never exceeds that node's allowance. Deploying such a budget needs a host that keeps the tree and mediates every spend; the account's grant API does not provide one, and we propose it as later work.

Containment also has a dynamic half. Grant lowering refuses any rule whose target is the account or a member of its excluded set: the adopted recovery controller, and the zero-knowledge adapter and pool of the account's recovery configuration, read from the account's storage at install time. Because the account may adopt a controller later, __check_auth rechecks each selected grant rule's call against the current set and refuses with ScopeEscalation. The install-time property has model and translation theorems; the recheck is tested shell code.
