The account decides each request at one point, and writes nothing unless the signature also checks.

{{ref:fig:fig-auth-path}} follows one request through a Perch account in six stages. (1) The host calls __check_auth with the payload, the rule named for each context and the claimed signers. (2) Guards refuse what the account never allows through a grant, such as a grant rule on its recovery contracts. (3) The account looks up each named rule and its spending record. (4) The decision function checks the request against the rules and computes the next spending records. (5) The signatures are checked: a verifier contract checks each external signer, and the host checks a delegated one. (6) The account stores the changed records, and the request is authorized. A refusal at any stage writes nothing. The verifier runs after the decision, so a request the grant refuses never reaches it.

{{fig:fig-auth-path}}

With JavaScript the figure lets you choose a request (a lost guess, a transfer within or over the cap, a call to the account), a signer, the grant's state and the rule named, and lights each stage in turn. When the decision accepts, it names the rule that allows each call: the witness that {{ref:stmt:acceptance-implies-permission}} promises.

The decision function

Stage 4 is rule_eval::authorize, the evaluator in rule-core {{fact:rule-core-pin-short}}. It takes the selected rules, their spending records, the contexts, the rule chosen for each context, the claimed signers, the ledger and the grant generation, and returns the next spending records or a Refusal. It reads no storage and checks no signature; the account code around it does both. The theorems in {{ref:sec:proofs}} are about this function.

A refusal reaches the caller as one of two codes inside {{fact:host-auth-error}}: auth error {{fact:auth-error-stale-scope}} for a grant issued before a completed recovery, and {{fact:auth-error-rule-eval-refused}} for every other refusal.

What a signature binds

An external signer signs a digest that binds this account and the selected rule IDs, so a relayer cannot move the signature to another rule the signer belongs to, such as an uncapped one. A delegated signer approves the host's payload, which names the account but not the rule IDs. OpenZeppelin {{fact:oz-v080-tag}} binds the rule IDs for both kinds, so on the delegated path it binds more than Perch.

For wallet and app developers

  • Simulate twice. Recording simulation does not call __check_auth, so it cannot predict a Perch refusal. Sign the entry with the selected rule IDs, then simulate again with enforcing authorization to learn the verdict and the final footprint.
  • Choose the rules. The payload names one installed rule per context in context_rule_ids, in context order.
  • Build documents. packages/perch-js builds validated grant documents and authorizations, and its requestToPolicyDoc turns an ERC-7715-shaped permission request {{cite:erc7715}} into a grant document (request.ts:1-11, 49). docs/schema.md describes a JSON Schema for documents.
  • Read refusals. A refusal reports auth error {{fact:auth-error-stale-scope}} or {{fact:auth-error-rule-eval-refused}} and nothing more; re-run the evaluator off chain to learn which context failed.
  • Try it. {{ref:sec:simulation}} runs the account in this page; the {{fact:wallet-name}} preview creates accounts on testnet.
