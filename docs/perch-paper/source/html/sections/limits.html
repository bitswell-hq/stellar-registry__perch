Proof-to-binary correspondence. The theorems are about the translation of the MIR that rustc nightly-2026-09-17 produces; rule-core's CI also builds the evaluator with rustc 1.99.0, Perch builds its contracts with rustc 1.97.1, and nothing checks the Wasm against the translation (Figure 10). Release builds keep overflow checks and abort on panic, and allocation failure and stack exhaustion, which the functional model omits, also trap, so each fails the transaction.

The specification we trust. The theorems relate the code to a specification that is itself trusted: the denotation functions that give translated values their meaning; the document meaning Doc.allows, written from Perch's earlier OpenZeppelin-based account (dff2a73, on the library at 33726766) and not re-derived from the pinned gate; and the Soroban host models.

The shell and the host. Tested, not proven: the JSON parser and compiler, stored-value decoding, rule-ID resolution, context conversion, assembly of the excluded set, spending-record persistence, the credential index, the generation update, the composition of evaluation with authentication, and the recovery controller's state machine. The integration tests that exercise them run the account's real __check_auth under enforcing authorization, but as natively registered contracts; the Wasm with passkeys and real proofs runs in Perch's release_stack.rs flows and on testnet. The host models are tested against selected traces, not proved equivalent to soroban-env-host, and leave out TTL, archival, fees, footprints and validation before the host runs (§09). This paper's simulator is another tested host integration.

Authentication, recovery and display. The account trusts its verifiers to check evidence, and the recovery controller its account document names to decide completions; unlike verifiers, the controller gets no registry provenance check, so wallets should pin the published controller's content address. The perch/verifiers registry's manager, which admits verifier names, is a single human-held key until a multisig and timelock are in place. Delegated signers do not bind rule selection, and the WebAuthn verifier does not bind an origin (§06). A wallet must show what the signed payload commits to.

Effects outside authorization. Rules mediate only actions whose authority passes through the account. A standing token allowance used by transfer_from, or funds held by another contract (such as the game's payout), can move value without a fresh authorization, and recovery, grant removal and the Protected freeze leave such allowances usable. A grant rule on a token contract that does not restrict its functions also allows approve. An owner-authorized execute(target, function, args) runs as the account, so the callee's require_auth passes by invoker authority and no rule or cap sees it; grants cannot reach execute, but an administrative rule that allows it has unlimited authority over the targets it permits. Policy evaluation provides no confidentiality or information-flow control.

Recovery and upgrades. Losing every factor the condition needs remains loss, and Protected without an enrolled baseline protects against a stolen owner key no better than Loss (§07). Outside an authorized recovery attempt, the owner may schedule a code upgrade and execute it after a fixed 120,960-ledger delay (seven days at the nominal five-second ledger); any change of the recovery generation makes the request stale, and under Protected the recovery condition must approve the exact Wasm hash. New code inherits the account's storage, including the revoked set and the generation, and nothing in the old code can make it honor them; the proofs cover the examined code, not replacement code.

Resources, state and open items. Bounded records and arithmetic can refuse a logically permitted action, and on chain a capped rule's window holds at most 907 spends (§04). Documents are capped at 8 signers, 10 rules, 8,192 canonical bytes and 20-byte rule names, so that a thief holding the owner key cannot make recovery too expensive to complete; the worst measured flow, a recovery completion at those caps, uses 40.7% of the 400M instruction limit, in process on the preview's bytes, and disk-read bytes are not yet measured. Replacing a capped rule, or changing its cap in either direction, starts an empty window, so lowering a cap from 10 to 5 right after spending 10 allows 5 more within the same window. The account's renew does not extend installed-rule records, so an idle account may need a restore before its next transaction (Table 4). No single theorem covers the whole pinned gate, including mixed administrative and grant batches, and no external audit has been completed (§02). One documented deferral bears on §07: the account consumes a completion marker by the target's canonical identity, not its exact bytes. If a completion authorization whose apply_doc never ran left a marker, an owner-authorized write of a differently spelled version of the same target in the same ledger is classified as the completion and runs its revocation, nullifier and generation effects (issue #15). It cannot install a different policy.
