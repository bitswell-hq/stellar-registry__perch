The proofs cover the decision function's translation, and a grant bounds only what passes through the account's authorization.

The proof boundary

The theorems are about the Lean translation of the Rust, not the compiled Wasm, and nothing checks one against the other. The specification is trusted. The account code around the function is tested, and no single theorem covers the whole authorization path.

Against a grantee

A key named by several rules holds the union of their authority, and caps are per rule, not per grant. Each call is checked alone ({{ref:fig:fig-contexts}}). A standing token allowance and the owner's execute move value outside any grant, and a grant rule on a token contract with no function list also allows approve. Replacing a capped rule starts an empty window, so lowering a cap right after the grantee spent up to it allows the new limit again in the same window. A window holds at most {{fact:spends-per-window}} spends.

Against a relayer

Delegated signers do not bind rule IDs. A rule edited in place between signing and inclusion decides under its new contents. A refused entry can be resubmitted until it expires. Grant installs take no expected version, so two pre-signed installs for one grant can land in either order.

Beyond these

Documents are capped at {{fact:doc-max-signers}} signers, {{fact:doc-max-rules}} rules and {{fact:doc-max-canonical-bytes}} canonical bytes, so a grant beyond those caps cannot be installed. No external audit has been done. Theft of the owner's key, recovery and the components the account trusts are discussed in the vision paper.
