The rule check is translated into Lean and proved to match a readable model; the code around it is tested.

The evaluator is about {{fact:rule-eval-lines}} lines of dependency-free, no_std Rust that forbids unsafe code. It is written in a subset that Aeneas can translate: no traits, closures or iterator adaptors, and every loop a while over one slice.

Three tools connect that Rust to proofs. The Rust compiler lowers code to MIR, its mid-level intermediate representation. Charon reads the MIR that rustc {{fact:rustc-mir-nightly}} produces, and Aeneas {{cite:aeneas}} translates it into a pure functional program in Lean, a proof assistant whose small kernel checks every proof. The translation is a generated {{fact:extracted-lean-lines}}-line Lean file, and equivalence theorems relate it to a readable model written by hand. rule-core's CI regenerates the translation and fails on any difference. It also pins the axioms of all {{fact:exported-theorems}} exported theorems: none uses more than Lean's three standard axioms ({{fact:standard-axioms}}), so none uses sorry, Lean's placeholder for a missing proof. A claims ledger, checked in CI, records {{fact:claims-total}} claims as proven ({{fact:claims-proven}}), tested ({{fact:claims-tested}}), assumed ({{fact:claims-assumed}}) or unproven ({{fact:claims-unproven}}).

Each statement names its object: rule-core's readable model; the translation; the account model, an abstract account with two events (apply a document, complete a recovery) and no Rust counterpart; the host model of Soroban's authorization, whose fidelity to the host is tested; or Perch's canonical-encoding package. Aeneas gives every translated function three outcomes, success, panic and divergence, so a theorem that a function succeeds on every input proves that it neither panics nor loops; Rust's Result<_, Refusal> is the value inside that success. This paper says proved only of statements Lean's kernel has checked.

How to read a statement card

  • Each card has a label, T1 to T{{fact:statements-count}}, which the academic edition shares; a title; the statement in words; and its evidence, the Lean names linked to their source.
  • The tag says what is proved about what. PROVED · TRANSLATION: a theorem about the Aeneas translation of the Rust. MODEL + TRANSLATION: the property proved for the model and for the translation. ACCOUNT MODEL, HOST MODEL and PERCH CANON PACKAGE: theorems about those objects, none of which is the compiled contract.
  • Some theorems carry hypotheses. Doc.Valid: the document is well formed in the sense the theorems define; that Perch's validator accepts only such documents is recorded as unproven. LowerRoom and ArgsRoom: the document's lists fit in the evaluator's bounded vectors, so lowering has room to run.
  • A translated value denotes the model value it stands for: the theorems relate the two through these denotation functions.

The proved functions run on chain: the account calls the translated lower and lower_scoped on install and rule_eval::authorize in __check_auth. Tests connect them to the shell. Perch's integration suite runs rule-core's {{fact:lean-doc-traces}} Lean-generated document traces through the account's real apply_doc, apply_scope and __check_auth, with the real Ed25519 verifier under enforcing authorization, and checks the stored rules against the lowering and every verdict and spending record against the model. Perch's CI also replays rule-core's conformance vectors. The cap theorem is stated over one fixed slice of rules, while the shell rebuilds local slices and indices for each authorization, so carrying the theorem through rule selection is an argued and tested obligation (O2), not a theorem.

What the account must do for the theorems to apply

The theorems hold for the evaluator. The account shell has obligations that carry them to the deployed account; each is tested or argued, not proved.

Together, T1, T2, T9 and T10 and obligations O1 to O6 give an argument, not a mechanized proof, that an authorization the account accepts under a grant is allowed by the grant's source document, calls neither the account nor its excluded set, and is refused after a completed recovery.

What the proofs trust

  • Lean's kernel and its three standard axioms.
  • Charon {{fact:charon-rev}}, Aeneas {{fact:aeneas-rev}}, and Aeneas's Lean library, which models Rust's primitives.
  • The MIR that rustc {{fact:rustc-mir-nightly}} produces.
  • The specification: the denotation functions, and the document meaning Doc.allows, written from Perch's earlier account at {{fact:doc-allows-source}}.
  • The host models, tested against {{fact:host-model-tested-versions}}.
  • rustc {{fact:rustc-perch}} and its WebAssembly back end, which build the deployed contract.
  • The account shell, verifiers and recovery controller, which are tested, and soroban-env-host.
