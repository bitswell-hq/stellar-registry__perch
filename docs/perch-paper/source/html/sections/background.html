On Soroban the account itself decides every call made in its name, one call at a time, and the signer names the rule that decides each one.

Authorization entries and contexts

A Soroban contract that needs an address's approval calls require_auth on it. When the address is a contract account, the host calls that account's __check_auth {{cite:cap-0046-11,stellar-custom-account}}. A transaction carries one authorization entry for each address whose approval it needs. For each entry the host passes the account a signature payload, a hash of the network ID, a nonce, a signature-expiration ledger and the entry's invocation tree, together with the entry's contexts: every call and contract creation in that tree, flattened in preorder, root first. The account must decide every context; approving the root alone would leave the rest unchecked.

The host consumes the nonce only when the transaction succeeds. A refused entry stays usable until its expiration ledger, so a capped transfer refused now can be resubmitted and succeed once the window has room.

A signer whose key the account checks itself, through a verifier contract, is an external signer. CAP-0071 {{cite:cap-0071}}, a Stellar Core Advancement Proposal, adds delegated signers: an address listed as a delegate approves for the account, the host authenticates it, and its approval rides in the account's own authorization entry and covers the host's signature payload.

Wallets simulate a transaction before signing it. Recording simulation, the RPC mode that discovers which authorizations a transaction needs, does not call __check_auth, for a Perch account or for an OpenZeppelin one, so it cannot predict a refusal. Both need a second, enforcing simulation with the signed entry to learn the verdict ({{ref:sec:authorization}}).

Two ideas from OpenZeppelin's account

OpenZeppelin's Soroban account library {{cite:oz-stellar-accounts}} defines the model that both Perch and oz-policy-builder build on.

  • Context rule. OpenZeppelin's unit of permission. It has a scope (Default, CallContract for one contract, or CreateContract), a name, an optional valid_until ledger, signers and policies. The signer's AuthPayload names one rule per context in context_rule_ids, and the account checks each context against the rule named for it. Signers are External or Delegated, as above.
  • Policy. A separate contract attached to a rule, with the hooks install, uninstall and enforce. In OpenZeppelin {{fact:oz-v080-tag}} the account validates the selected rules, authenticates their signers, and then calls every attached policy's enforce, in the order of the policies' contract addresses.

Perch uses the same context_rule_ids field and the same two signer kinds, but it attaches no policies: the account decides by itself ({{ref:sec:authorization}}). Three more ideas, needed for the comparison, wait for {{ref:sec:compare}}.
