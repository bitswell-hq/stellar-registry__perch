On Soroban the account itself decides every call made in its name, one call at a time, and the authorization payload names the rule for each call.

Authorization entries and contexts

A Soroban contract that needs an address's approval calls require_auth on it. When the address is a contract account, the host calls that account's __check_auth {{cite:cap-0046-11,stellar-custom-account}}. A transaction carries one authorization entry for each address whose approval it needs, except CAP-0071 delegates (below). For each entry the host passes the account a signature payload, a hash of the network ID, a nonce, a signature-expiration ledger and the entry's invocation tree, together with the entry's contexts: every call and contract creation in that tree, flattened in preorder, root first. The account must decide every context; approving the root alone would leave the rest unchecked.

The host consumes the nonce only when the transaction succeeds. A refused entry stays usable until its expiration ledger, so a capped transfer refused now can be resubmitted and succeed once the window has room.

A signer whose key the account checks itself, through a verifier contract, is an external signer. CAP-0071 {{cite:cap-0071}}, a Stellar Core Advancement Proposal, adds delegated signers: an address listed as a delegate approves for the account, the host authenticates it, and its approval rides in the account's own authorization entry and covers the host's signature payload.

Wallets simulate a transaction before signing it. Recording simulation, the RPC mode that discovers which authorizations a transaction needs, does not call the account's __check_auth, so it cannot predict a refusal; a wallet needs a second, enforcing simulation with the signed entry to learn the verdict ({{ref:sec:authorization}}).

Two ideas from OpenZeppelin's account

OpenZeppelin's Soroban account library {{cite:oz-stellar-accounts}} defines the model that oz-policy-builder builds on and whose authorization types Perch reproduces.

  • Context rule. OpenZeppelin's unit of permission. It has a scope (Default, CallContract for one contract, or a contract-creation scope), a name, an optional valid_until ledger, signers and policies. The signer's AuthPayload names one rule per context in context_rule_ids, and the account checks each context against the rule named for it. Signers are External or Delegated. OpenZeppelin {{fact:oz-v080-tag}} checks a Delegated signer with require_auth_for_args, in an authorization entry of its own; Perch checks one through CAP-0071, inside the account's entry. That separate entry is how OpenZeppelin binds rule IDs for delegated signers ({{ref:tab:tab-binding}}).
  • Policy. A separate contract attached to a rule, with the hooks install, uninstall and enforce. In OpenZeppelin {{fact:oz-v080-tag}} the account validates the selected rules, refuses a signer on none of them, authenticates the signers, and then calls every attached policy's enforce in the rule's stored order: address order for the policies the rule was created with, then any added later.

Perch uses the same context_rule_ids field and the same two signer kinds, checked as above, but it attaches no policies: the account decides by itself ({{ref:sec:authorization}}). Three more ideas, needed for the comparison, wait for {{ref:sec:compare}}.

A lost guess produces two contexts, the game's guess and the XLM transfer the game makes from the account, and the authorization payload names one installed rule for each; the capped rule charges the transfer. A win produces the root alone, because the game pays from its own balance. Because each context is checked alone, a direct transfer within the cap, with no game call, is also allowed.
