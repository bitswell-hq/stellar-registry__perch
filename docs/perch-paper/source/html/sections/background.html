On Soroban the account itself approves every call made in its name, and it decides each call alone.

How Soroban asks an account

A Soroban contract that needs an address's approval calls require_auth on it. When the address is a contract account, the host, the program that runs contracts for the network, calls that account's __check_auth {{cite:cap-0046-11,stellar-custom-account}}. So in the shop grant the app never calls the account: it calls the XLM contract's transfer(from, to, amount) with the account as from, and transfer's require_auth makes the host ask the account ({{ref:fig:fig-sim}} shows this order in its traces). A transaction carries one authorization entry for each address whose approval it needs. For each entry the host passes __check_auth three things: the payload hash, which signatures cover; an auth payload, whose shape the account defines (here the signatures and context_rule_ids, one chosen rule per context); and the entry's contexts: every call and contract creation in its invocation tree, in preorder (each call before the calls it makes). The account must decide every context. The host consumes the entry's nonce, a one-time number that stops replay, only when the transaction succeeds, so a refused entry can be resubmitted until it expires.

A signer whose key the account checks itself, through a verifier contract, is an external signer. A delegated signer is another address that approves through the host; CAP-0071 {{cite:cap-0071}}, a Core Advancement Proposal, lets that approval ride in the account's own entry. In OpenZeppelin {{fact:oz-v080-tag}} a delegated signer instead approves in an entry of its own, which also binds the rule IDs. Wallets simulate a transaction before signing it, but recording simulation, the mode that discovers which entries a transaction needs, does not call __check_auth, so it cannot predict a refusal. Enforcing simulation, which runs __check_auth, can.

OpenZeppelin's account

OpenZeppelin's Soroban account library {{cite:oz-stellar-accounts}} gives both designs their vocabulary. A context rule is its unit of permission: a scope (for example one contract), an optional expiry, signers and policies. The auth payload names one rule per context in context_rule_ids, and signers are External or Delegated, as above. A policy is a separate contract attached to a rule; its enforce hook runs on each call the rule approves. In {{fact:oz-v080-tag}} the account validates the selected rules, authenticates the signers, and then calls each policy's enforce (storage.rs:629-690).

oz-policy-builder

oz-policy-builder {{cite:oz-policy-builder}} writes rules for OpenZeppelin accounts and has two halves (README.md:13-24). Off chain, a synthesiser records a transaction or takes a declared intent and writes a predicate, a declarative condition on one call. On chain, a shared policy-interpreter contract, attached to a context rule as a policy, evaluates the predicate on every guarded call. The interpreter decides each call alone and keeps no totals; limits over time come from a token allowance with an expiry, or from OpenZeppelin's spending_limit policy beside the interpreter (docs/stellar.md:404-407).

One authorization, several contexts

{{ref:fig:fig-contexts}} shows one authorization from the account's side, using a game grant. The app may call a game's guess and transfer at most {{fact:grant3-cap-xlm}} XLM per {{fact:grant3-period-ledgers}} ledgers to any recipient, since the grant's transfer rule pins none. A lost guess produces two contexts, the game's guess and the transfer the game makes from the account, and the auth payload names one rule for each. A win authorizes the guess alone, because the game pays from its own balance. Because each context is checked alone, a direct transfer within the cap, to the game or to anyone else, is also allowed.
