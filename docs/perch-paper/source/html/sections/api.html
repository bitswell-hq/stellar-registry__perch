Two functions in the artifacts are named check_auth: Soroban's __check_auth entry point, and the shell function perch_smart_account::check_auth that it calls, which runs the guards of §06 and then the evaluator. This paper calls the evaluator itself rule_eval::check_auth; at the pin it is rule_eval::authorize(rules, records, contexts, choices, authenticated, now, generation) -> Result<Vec<SpendRecord>, Refusal> in rule-core cbabe59, called from the account's gate.rs. The first listing below is this paper's illustrative interface, which groups the seven arguments as EvaluationInput; it is not a function in the artifacts, and a wrapper with that signature would need its own correspondence argument. The second is the pinned call. The evaluator returns next_records, aligned with the input rules, or a Refusal; it neither searches for rules nor verifies signatures.

// This paper's illustrative interface; pinned symbol: rule_eval::authorize (seven arguments)
let evaluated = rule_eval::check_auth(EvaluationInput {
    rules: &selected_rules,
    spend_records: &before,
    contexts: &contexts,
    rule_indices: &indices, // local indices, not installed IDs
    signer_identities: &claimed_signers,
    ledger: current_ledger,
    generation: grant_generation,
})?;

// Account-shell responsibilities:
authenticate_bound_payload(&payload)?;
store_selected_records(&installed_rule_ids, evaluated.next_records);
// Pinned build: perch-smart-account/src/gate.rs, calling rule-core cbabe59
let after = rule_eval::authorize(
    &rules,                 // the selected rules, each once
    &records,               // their spending records
    &contexts,              // host contexts, converted
    &choices,               // one local rule index per context
    &signers,               // claimed signer identities
    e.ledger().sequence(),
    scope_generation(e),    // the grant generation
)
.map_err(|r| match r {
    rule_eval::Refusal::StaleGeneration => PerchAuthError::StaleScope.into(),
    _ => refused(),         // RuleEvalRefused
})?;

The engine refuses misaligned inputs, an expired, stale or non-matching rule, an unused signer, or a failed charge, each as a distinct Refusal. The account keeps one distinction: a stale grant becomes StaleScope (auth error 3) and every other refusal RuleEvalRefused (auth error 5), __check_auth codes that the host reports inside Error(Auth, InvalidAction) and logs in its diagnostic events; a wallet that needs the reason re-runs the evaluator off chain. The engine accepts an empty batch vacuously, but the host never passes zero contexts (§09), so the stale-grant statements are stated for nonempty batches.
