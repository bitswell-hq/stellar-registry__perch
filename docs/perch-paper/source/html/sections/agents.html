We propose applying the same separation to an agent runtime: a pure engine decides whether an action is permitted and computes its accounting effect; a host mediates the action and commits state. The rule model is generic in action and signer types, and the evaluator can execute outside Soroban. That provides a basis for studying chain, file, network and signing permissions under one policy model.

In the proposed architecture, a root agent holds a Perch grant on a Stellar account. It derives child grants from its parent authority, with budgets (§04) and file, network, signing and spawn permissions. Agents hold no signing keys: a separate host and key service mediate signing, and the account independently rechecks the resulting payments and signature authorizations. We propose x402 on Stellar as a payment integration for that runtime. This architecture is a proposed extension; the browser experiment implements none of its process, spawn or payment-protocol machinery.

The extracted chain vocabulary does not already implement filesystem or network authority. A file rule needs canonical, component-aware paths rather than raw string prefixes; a network rule needs host, port and redirect semantics; a signing rule needs decoded payload semantics. Time must come from a monotone source, and rate limits may require per-call charges rather than an amount argument. Each addition needs a specification, implementation correspondence and test vectors.

Process isolation is another layer. A runtime must prevent direct filesystem, socket and signing access around the policy host, bind actions to the intended agent, handle races between validation and execution, and persist accounting atomically. A theorem that the evaluator refuses an action cannot prove that a process lacks another route to perform it. Nido's separate grant-evaluation work provides an integration direction, but this Perch browser example implements only the chain/account scenario.

We propose exploring Cedar as an authoring language for a restricted Perch policy fragment. The Cedar walkthrough’s Perch section describes the offline compiler prototype, its accepted and rejected inputs, and the validation and proof work still required. This is proposed work, not a deployed Cedar integration.
