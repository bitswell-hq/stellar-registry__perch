Everything in this section is proposed, not built.

We propose applying the same separation to an agent runtime: a pure engine decides whether an action is permitted and computes its accounting effect, and a host mediates the action and commits state. The rule model is generic in action and signer types, and the evaluator can run outside Soroban. In the proposed architecture, a root agent holds a Perch grant on a Stellar account and derives child grants from it, with budgets and with file, network, signing and spawn permissions. Agents hold no signing keys: a separate host and key service mediate signing, and the account independently rechecks the resulting payments and signature authorizations. For payments we propose x402, a protocol that carries payments in HTTP using the 402 Payment Required status, on Stellar.

Each new kind of permission needs a specification, implementation correspondence and test vectors. A file rule needs canonical, component-aware paths rather than raw string prefixes; a network rule needs host, port and redirect semantics; a signing rule needs decoded payload semantics. Process isolation is a separate layer: a theorem that the evaluator refuses an action cannot prove that a process lacks another route to perform it.

A delegation-tree budget charges spending to ancestors: child allowances may oversubscribe a parent, yet spending beneath each node never exceeds that node's allowance (T7, a model result). Deploying it needs a host that keeps the tree and mediates every spend, which the account's grant interface does not provide. We propose:

  • a runtime for delegation-tree budgets, and an account entry point that installs attenuated grants;
  • exact authorization-entry roots, now in draft ({{fact:exact-roots-prs}}), so that a transfer rule can require its entry's root;
  • Cedar as an authoring language for a restricted Perch policy fragment; the Cedar walkthrough's Perch section describes an offline compiler prototype, its accepted and rejected inputs, and the validation and proof work still required;
  • checking this paper's proofs in the page, with a Lean kernel checker compiled to WebAssembly ({{ref:sec:repro}});
  • extending the walkthrough's run ({{ref:tab:tab-walkthrough}}) to a comparative measurement of Perch and oz-policy-builder with exact metering in one harness (soroban-sim, one host version, Ed25519 signers), reporting CPU, memory, I/O, fees and cross-contract calls for five workloads: one capped transfer, a losing guess, one install, ending authority over many grants, and storage after many transfers;
  • exporting the entry-point names this paper uses ({{ref:tab:tab-api}}).
