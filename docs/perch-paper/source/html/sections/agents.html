Everything in this section is proposed, not built.

We propose applying the same separation to an agent runtime: a pure engine decides whether an action is permitted and computes its accounting effect, and a host mediates the action and commits state. The rule model is generic in action and signer types, and the evaluator can run outside Soroban. In the proposed architecture, a root agent holds a Perch grant on a Stellar account and derives child grants from it, with budgets and with file, network, signing and spawn permissions. Agents hold no signing keys: a separate host and key service mediate signing, and the account independently rechecks the resulting payments and signature authorizations. For payments we propose x402, a protocol that carries payments in HTTP using the 402 Payment Required status, on Stellar.

Each new kind of permission needs a specification, implementation correspondence and test vectors. A file rule needs canonical, component-aware paths rather than raw string prefixes; a network rule needs host, port and redirect semantics; a signing rule needs decoded payload semantics. Process isolation is a separate layer: a theorem that the evaluator refuses an action cannot prove that a process lacks another route to perform it.

A delegation-tree budget charges spending to ancestors: child allowances may oversubscribe a parent, yet spending beneath each node never exceeds that node's allowance (T7, a model result). Deploying it needs a host that keeps the tree and mediates every spend, which the account's grant interface does not provide. We propose:

  • a runtime for delegation-tree budgets, and an account entry point that installs attenuated grants;
  • exact authorization-entry roots, now in draft ({{fact:exact-roots-prs}}), so that a transfer rule can require its entry's root;
  • Cedar as an authoring language for a restricted Perch policy fragment, described below; the Cedar walkthrough's Perch section describes an offline compiler prototype, its accepted and rejected inputs, and the validation and proof work still required;
  • a recording front end that, like oz-policy-builder's synthesiser, starts from a recorded transaction and emits a Perch grant document for the owner to review ({{ref:sec:compare}});
  • checking this paper's proofs in the page, with a Lean kernel checker compiled to WebAssembly ({{ref:sec:repro}});
  • a comparative measurement of Perch and oz-policy-builder with exact metering in one harness (soroban-sim, one host version, Ed25519 keys), reporting CPU, memory, I/O, fees and cross-contract calls for five workloads: one capped transfer, a losing guess, one install, ending authority over many grants, and storage after many transfers. The walkthrough ({{ref:tab:tab-walkthrough}}) ran one task without exact metering; it is not the first of these workloads;
  • exporting the entry-point names this paper uses ({{ref:tab:tab-api}}).

A proved bridge from Cedar (proposed, not under way). The Lean library of cedar-spec {{cite:cedar-spec}}, Cedar's formal specification, loads unchanged into the Lean toolchain of rule-core's proofs {{cite:rule-core}}. Both semantics are total definitional interpreters, Lean functions rather than relations, so a simulation between them is one commuting equation: Cedar's verdict on an encoded request equals rule-core's verdict on the compiled rule. In an unpublished experiment we proved that equation for a cut-down fragment, with no sorry, and composed Cedar's allowed_iff_explicitly_permitted_and_not_denied, the fragment's simulation and rule-core's allows_eq down to the extracted Rust. Perch would borrow Cedar's specification as a source language, not its large proofs. The proposed route is a compiler from a Cedar fragment to rule-core rules, verified in Lean against Cedar's semantics, with each installed rule set checked in Lean's kernel against that compiler. Three limits are known. cedar-spec and Aeneas each fix a Lean version, so the two must move in step. Cedar's integers are 64-bit, so the bridge holds only for amounts in that range, not for every i128. And Cedar's parser is tested against its specification, not proved.
