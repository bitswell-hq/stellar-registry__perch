oz-policy-builder composes a decision from separate contracts; Perch makes it at one point. Each arrangement buys something the other gives up.

This section compares Perch with oz-policy-builder {{cite:oz-policy-builder}} at {{fact:opb-pin-short}}, on OpenZeppelin {{fact:oz-v080-tag}}, from its public documentation and source. It is a trade-off, not a contest.

Shared ground

Both build on OpenZeppelin's context-rule model and its context_rule_ids field. Both judge each call alone: oz-policy-builder's interpreter "sees one authorised call at a time" (docs/architecture.md:307-309), and so does a Perch rule ({{ref:fig:fig-contexts}}, case c). Both deny by default.

Two arrangements

An OpenZeppelin account with oz-policy-builder composes its decision from contracts that can be swapped and audited separately: the account's own checks, then the interpreter, spending_limit and any threshold policy attached to the rule. Its README calls the interpreter "one audit-once engine": every policy is data fed into it, so a new combination of constraints needs no new contract and no re-audit (README.md:13-24). Perch puts one document behind one decision point in the account. Composition buys flexibility; one decision point gives one place to check. {{ref:fig:fig-compose}} models the same five checks both ways.

{{fig:fig-compose}}

With JavaScript you can attach, detach and reorder the policies in (b) and send the same requests through both arrangements. A live read, such as an oracle price, fits only (b): a Perch rule reads nothing outside the account.

A limit over time

oz-policy-builder's interpreter judges each call and keeps no totals. Its documentation says that amount limits over time come from a token allowance and its expiry, or from OpenZeppelin's spending_limit beside the interpreter (docs/stellar.md:404-407). spending_limit is a separate, opt-in policy that refuses every function but transfer, so the synthesiser installs it only on a rule pinned to transfer (install.ts:957-967). In Perch the window is part of the rule and is charged in the same decision ({{ref:stmt:cap-window-safety}}). {{ref:sec:simulation}} runs both designs with and without spending_limit.

Where each is stronger

oz-policy-builder

  • Maturity. Its interpreter is pinned on testnet; an external audit of {{fact:opb-release}} has been in progress since {{fact:opb-audit-start}}; its off-chain packages were hardened after a penetration test (PR {{fact:opb-pentest-pr}}); and a corpus test takes {{fact:opb-corpus-calls}} mainnet contract calls of {{fact:opb-corpus-shapes}} shapes through synthesis to the interpreter. Perch's design is unmerged, a testnet preview, and unaudited.
  • Authoring. Record a transaction or declare an intent; synthesise a minimal predicate; verify it against the deployed interpreter's check; review; install unsigned. A CLI and an MCP server expose the same {{fact:opb-tools-count}} tools to shells and agents. A Perch author writes the grant document.
  • Expressiveness and ecosystem fit. Or, comparisons, quantifiers over lists, ledger-clock windows, slippage floors (a minimum a swap must return) and reads of other contracts; OpenZeppelin's threshold policies and other add-ons; a deny code for each reason; rule IDs bound for delegated signers.

Perch

  • Limits over time. The window is part of the rule's decision, not an optional policy beside it. Caveat: the bound is proved for the decision function's translation, from empty records; rule selection and storage are tested.
  • One decision point. One contract holds the rules and their state, decides before any verifier runs, installs one document across several contracts, and accepts passkey signers on grant rules. Caveat: the account code around the decision is tested, not proved, and nothing is audited.
  • A proved core. Theorems 1, 2, 4, 6 and 8 hold for the Lean translation of the decision function ({{ref:sec:proofs}}). Caveat: the compiled contract is not proved, and nothing is audited.

Lessons for Perch

We propose five things to take from oz-policy-builder:

  1. Recording as authoring. A front end that records a transaction and emits a grant document for the owner to review.
  2. Simulate before install. Run the account's own evaluator in enforcing simulation before a grant is installed, as oz-policy-builder verifies a predicate against the deployed check.
  3. Minimality checks. Flag rules wider than the recording they came from.
  4. A corpus of real transactions. Run recorded mainnet transactions through Perch's lowering and evaluator.
  5. An audit before claiming maturity. An external audit before Perch holds real funds.

This section reads both designs from source and runs one task; it measures no costs. The companion paper Perch and oz-policy-builder sets out every dimension with sources, the recorded walkthrough and one intent spelled both ways.
