Does the account enforce what the design says?

In the recorded run of {{ref:sec:simulation}}, the two designs gave the same verdict on every request except the three payments under the per-call bound alone, a configuration the owner chose by removing spending_limit. A native run, a WASI build and this page give the same replies. Beyond that run, rule-core generates {{fact:lean-doc-traces}} document traces from its Lean model, and Perch's tests run them through the natively compiled account and compare every verdict and spending record with the model.

On Stellar testnet

On {{fact:nido-run-date}}, a scripted browser run of the {{fact:wallet-name}} wallet's preview, with virtual passkeys, made {{fact:nido-run-transactions}} successful testnet transactions. It installed a game's two-rule grant, whose transfer rule pays the game alone, and made two lost guesses. The wallet declined a third guess before signing because it would exceed the cap, so that refusal was the wallet's, not the chain's. The run also took a one-guardian recovery to completion. The game ran from a development branch with an uncommitted patch.

What does it cost? Perch alone

On the testnet preview, an XLM transfer through a grant rule, signed by a passkey, paid a fee of {{fact:smoke-fee-stroops}} stroops ({{fact:stroops-per-xlm}} stroops make one XLM), WebAuthn verification included. An account holding the game's grant pays {{fact:census-rent-xlm-year}} XLM a year in rent at the network's floor rate. These are Perch's figures alone; we compare no costs across designs.

One task, one host version without exact metering, different signer kinds in the two designs, periodic testnet resets and the patched game all limit what these results show.
