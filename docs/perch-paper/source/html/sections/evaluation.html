We ran the account's contracts on a local Soroban host and on Stellar testnet, and every command gave its expected result.

Does the built account enforce what the design states?

The reference run executes {{fact:run-commands}} commands against the built account, document compiler, Ed25519 verifier and recovery controller in soroban-sim {{cite:soroban-sim}}, a portable Soroban host. {{ref:tab:tab-run}} lists each command's expected result, and the live experiment reproduces the run in this page. The native command-line program and the browser build use the same Rust driver and pinned contract bytes, and they agree on every returned field but wall-clock time.

The {{fact:run-commands}} commands submit {{fact:run-transactions}} transactions: {{fact:run-setup-transactions}} setup transactions, {{fact:run-game-deploy-transactions}} that upload and deploy the game, and {{fact:run-operation-transactions}} operations. Another {{fact:run-refused-in-simulation}} operations are refused in enforcing simulation, never submitted, and leave the ledger entries unchanged; {{fact:run-view-only}} command only advances the ledger. The run ends with {{fact:run-final-balance-xlm}} demo XLM ({{fact:run-balance-path}}) and grant generation {{fact:run-final-generation}}. Beyond this run, the {{fact:lean-doc-traces}} Lean-generated traces exercise the account's real entry points; {{ref:sec:proofs}} sets out what is proved, what is tested and what is trusted.

Method

Setup loads protocol-{{fact:sim-protocol}} cost and configuration entries from a testnet fixture (ledger {{fact:fixture-ledger}}; testnet now runs protocol {{fact:testnet-protocol}}) with the standalone passphrase and fresh local identities. It places the compiler and the Perch {{fact:perch-deployed-account-version}} policy contracts at the addresses the account derives from its build-time pins. A {{fact:registry-stub-bytes}}-byte registry stub returns the Ed25519 verifier hash for any requested version, so the account document can name its verifier {{fact:sim-verifier-name}} offline; the production registry's governance and version resolution are not tested. Grant documents name the verifier by address. Signers are software Ed25519 keys, and recovery uses real guardian signatures; no zero-knowledge or passkey flow runs.

The driver does not submit a refusal it catches during enforcing preflight, so the unchanged-state observation includes that preflight behaviour; it is not a claim that a failed, submitted network transaction pays no fee. After each step the page shows a ledger-entry fingerprint: a hash over the sorted keys, entry XDR and live-until values of every entry the session has written. It does not cover the simulator's clock, so advancing ledgers can change validity without changing the fingerprint.

The same contract source on Stellar testnet

On {{fact:nido-run-date}} a scripted browser run of the Nido preview, with virtual passkeys, made {{fact:nido-run-transactions}} successful testnet transactions across a user account and a guardian account: account creation; an account document adding a delegated administrative signer and naming the passkey verifier {{fact:verifier-name-webauthn}}; the game's two-rule grant, whose transfer rule pays the game alone; two lost guesses; and a one-guardian Loss recovery through to completion. What does it cost? Perch alone

{{ref:tab:tab-run}} gives the host CPU instructions of each applied transaction, including __check_auth and verifier calls; the build omits soroban-sim's exact-metering host, so counts can differ from stellar-core metering. On the testnet preview, a fresh account holding the game's two-rule grant after two capped transfers stores {{fact:census-bytes}} bytes in {{fact:census-entries}} ledger entries, {{fact:census-rent-xlm-year}} XLM a year in rent at the network's floor rate. In a smoke test on the same deployment, an XLM transfer of {{fact:smoke-amount}} through a grant rule, signed by a passkey, declared {{fact:smoke-cpu}} CPU instructions and paid a fee of {{fact:smoke-fee-stroops}} stroops; that figure includes WebAuthn verification.
