The experiment below runs the built account, document compiler, Ed25519 verifier and recovery controller as contract WebAssembly inside soroban-sim, itself a WASI reactor in a browser worker, on a local protocol-29 ledger; no wallet, real credential, RPC request or network transaction is involved. After each step the page shows a ledger-entry fingerprint, a hash over the sorted keys, entry XDR and live-until values of every entry the session has written.

Table 7 lists what each of the 27 reference commands should show, numbered as in Appendix A. Completion is allowed only from 10 ledgers after the second guardian approval, so advance 11 before completing. Step 4 calls the actual Guess the Number contract, whose secret is drawn from 1 to 10, so a guess of 0 always loses; its winning-number helper reads the simulator's storage and is a harness fixture, not a game method.

Method and reproducible results

The native command-line program and the browser reactor use the same Rust driver and pinned contract bytes. The 27 commands submit 27 transactions: 11 setup transactions in reset, 2 that upload and deploy the game, and 14 operations. Another 11 operations are refused in enforcing simulation, never submitted, and leave the ledger entries unchanged; one command only advances the ledger. Native and WASI runs agree on every returned field but wall-clock time. The final balance is 93 demo XLM (100 − 6 − 2 − 1 − 1 + 3) and the grant generation is 1; Appendix A embeds the sequence and hashes.

A refusal during enforcing preflight is not submitted by this driver. The unchanged-state observation therefore includes that preflight behavior; it is not a claim that a failed, submitted network transaction pays no fee. The fingerprint covers the sorted overlay ledger keys, entry XDR and live-until values, not the passage of the simulator's clock. Advancing ledgers can change validity without changing that fingerprint.

The same contract code on Stellar testnet

On 5 November 2026 a scripted browser run of Nido's preview (§02), with virtual passkeys, made 11 successful testnet transactions across a user and a guardian account: account creation, an account document adding a delegated administrative signer and naming the passkey verifier perch-webauthn-verifier@0.1.2, the game's two-rule grant (its transfer rule pays only the game), two lost guesses, and a one-guardian Loss recovery through to completion. The completion replaced the passkey and moved the grant generation to 1 and the recovery generation to 2 (§02). The wallet declined a third guess before signing because it would exceed the cap: the refusal was the wallet's, not the chain's. The game ran locally, from a development branch with an uncommitted patch.

In a separate smoke test on the same deployment, a 1-stroop XLM transfer from another account, through a grant rule and signed by a passkey, declared 5,944,258 CPU instructions and paid a fee of 12,889 stroops (transaction 3e652c73…). That figure includes WebAuthn verification and is not comparable with Table 8.
