soroban-sim runs the real contract code of both designs in this page, offline; you choose the requests.

soroban-sim {{cite:soroban-sim}} is a portable Soroban host: the host library the network runs (soroban-env-host {{fact:soroban-env-host-sim}}, here at protocol {{fact:sim-protocol}}; testnet now runs protocol {{fact:testnet-protocol}}), packaged so that a program or a web page can run contracts without a network. The simulation keeps one session per design and applies each request with enforcing authorization, the mode in which the host calls __check_auth. Its host is soroban-env-host built with the recording_mode feature, not the exact-metering build soroban-sim also offers, so costs are not exact. Each session holds:

  • for OpenZeppelin, the {{fact:oz-v080-tag}} account, oz-policy-builder's policy-interpreter, and OpenZeppelin's spending_limit;
  • for Perch, the account, its document compiler and its Ed25519 verifier;
  • in both, the native XLM contract.

The contracts are built from the pinned sources. The OpenZeppelin account, spending_limit and interpreter have the bytes oz-policy-builder records on testnet; the Perch account is the pinned build, not the testnet preview's. {{ref:sec:repro}} gives every hash. Both accounts install the shop grant's rule. On the OpenZeppelin side it is the predicate oz-policy-builder's synthesiser writes from our intent, which pins the recipient and bounds each transfer at {{fact:sim-oz-per-call-bound-xlm}} XLM, with spending_limit at {{fact:shop-cap-xlm}} XLM per {{fact:shop-period-ledgers}} ledgers beside it. On the Perch side it is one grant with the recipient pinned and the same cap.

For each request the page shows the verdict and code; the authorization trace, from the host's diagnostic events; the authorization entries; the window; a fingerprint of the ledger entries, which a refusal leaves unchanged (a refusal is never submitted); and whether the reply matches the recorded native run.

The signers differ, by design. The OpenZeppelin side signs as a delegated Stellar account, because the interpreter refuses an external signer on the rules it polices (error {{fact:opb-error-external-signer}}); that is why its requests carry a second authorization entry, in which the delegated signer approves. The Perch side signs with an Ed25519 key that a verifier contract checks. This is not a cost comparison, and the page shows no instruction counts.

The recorded scenario

{{ref:fig:fig-sim}} and {{ref:tab:tab-sim}} record this run:

  • The app pays the shop {{fact:sim-pay-xlm}} XLM, and both designs apply it. It then pays {{fact:sim-second-pay-xlm}} XLM in the same window, and both refuse: Perch in its decision, with no verifier call; the OpenZeppelin account in spending_limit (error {{fact:oz-spending-limit-exceeded}}).
  • The owner removes spending_limit from the OpenZeppelin rule. The per-call bound then applies each of {{fact:sim-oz-percall-sends}} {{fact:sim-pay-xlm}}-XLM payments, {{fact:sim-oz-percall-moved-xlm}} XLM within a few ledgers. Perch refuses all {{fact:sim-oz-percall-sends}}, because its window already holds {{fact:sim-pay-xlm}}. oz-policy-builder documents limits over time as coming from a token allowance and its expiry, or from spending_limit beside the interpreter (docs/stellar.md:404-407); removing it is a configuration the owner chose.
  • Adding spending_limit back starts it with an empty history, as replacing a Perch rule starts an empty window.
  • A payment to another recipient, a signature by another key in the app's name, and a key not on the rule are refused by both.
  • After {{fact:shop-period-ledgers}} ledgers, {{fact:sim-late-pay-xlm}} XLM applies in both.

Once the simulation runs here, each request card says whether its reply matches the native run, and a running count gives how many replies on the reference path match. The full simulation page has the reference table and each contract's Wasm hash; compare them with {{ref:sec:repro}}.

Why soroban-sim

  • Real contract bytes. Both designs run as WebAssembly compiled from the pinned sources, not as models.
  • Offline and deterministic. The page needs no network, and the same commands give the same replies.
  • Three runs agree. A native run, a WASI build (WebAssembly outside the browser) and this page give identical replies on every request once timings are removed (the replies' SHA-256 is in {{ref:sec:repro}}).
  • Inspectable traces. Each request lists the contracts it called, from the host's diagnostic events.
  • Two designs in one host. Both accounts run on the same host version and network settings.
