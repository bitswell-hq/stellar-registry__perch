soroban-sim runs the real contract code of both designs in this page, offline; you choose the requests.

soroban-sim {{cite:soroban-sim}} is a portable Soroban host: the host library the network runs (soroban-env-host {{fact:soroban-env-host-sim}}), packaged so that a program or a web page can run contracts without a network. The simulation keeps one session per design and applies each request with enforcing authorization, the mode in which the host calls __check_auth. It uses the recording-mode build of the host, so it does not meter costs exactly. Each session holds:

  • for OpenZeppelin, the {{fact:oz-v080-tag}} account, oz-policy-builder's policy-interpreter, and OpenZeppelin's spending_limit;
  • for Perch, the account, its document compiler and its Ed25519 verifier;
  • in both, the native XLM contract.

The contracts are built from the pinned sources; the interpreter's bytes are those oz-policy-builder pins on testnet, and every hash is in {{ref:sec:repro}}. Both accounts install the shop grant's rule. On the OpenZeppelin side it is the predicate oz-policy-builder's synthesiser writes, which pins the recipient and bounds each transfer at {{fact:shop-cap-xlm}} XLM, with spending_limit at {{fact:shop-cap-xlm}} XLM per {{fact:shop-period-ledgers}} ledgers beside it. On the Perch side it is one grant with the recipient pinned and the same cap.

For each request the page shows the verdict and code; the authorization trace, from the host's diagnostic events; the authorization entries; the window; a fingerprint of the ledger entries, which a refusal leaves unchanged; and whether the reply matches the recorded native run.

The signers differ, by design. The OpenZeppelin side signs as a delegated Stellar account, because the interpreter refuses an external signer on the rules it polices (error {{fact:opb-error-external-signer}}); that is why its requests carry a second authorization entry, in which the delegated signer approves. The Perch side signs with an Ed25519 key that a verifier contract checks. This is not a cost comparison, and the page shows no instruction counts.

The recorded scenario

{{ref:fig:fig-sim}} and {{ref:tab:tab-sim}} record this run:

  • The app pays the shop 6 XLM, and both designs apply it. It then pays 5 XLM in the same window, and both refuse: Perch in its decision, with no verifier call; the OpenZeppelin account in spending_limit (error {{fact:oz-spending-limit-exceeded}}).
  • The owner removes spending_limit from the OpenZeppelin rule. The per-call bound then applies each of {{fact:sim-oz-percall-sends}} 6-XLM payments, {{fact:sim-oz-percall-moved-xlm}} XLM within a few ledgers. Perch refuses all three, because its window already holds 6. oz-policy-builder documents spending_limit as the way to add a total (docs/stellar.md:404-407); removing it is a configuration the owner chose.
  • Adding spending_limit back starts it with an empty history, as replacing a Perch rule starts an empty window.
  • A payment to another recipient, a signature by another key in the app's name, and a key not on the rule are refused by both.
  • After {{fact:shop-period-ledgers}} ledgers, 5 XLM applies in both.

Once the simulation runs here, the reference rows carry a "matches the native run" mark, and its sources panel lists each contract's Wasm hash; compare them with {{ref:sec:repro}}.

Why soroban-sim

  • Real contract bytes. Both designs run as WebAssembly compiled from the pinned sources, not as models.
  • Offline and deterministic. The page needs no network, and the same commands give the same replies.
  • Three runs agree. A native run, a WASI build (WebAssembly outside the browser) and this page give identical replies on every request once timings are removed (the replies' SHA-256 is in {{ref:sec:repro}}).
  • Inspectable traces. Each request lists the contracts the host called while the account decided.
  • Two designs in one host. Both accounts run on the same host version and network settings.
